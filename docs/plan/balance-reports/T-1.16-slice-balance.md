## Tuning changes and the evidence for each

### 1. Crate rewards: fewer Charms and Keys (`src/config/drops.ts`)

| Rarity | Charm chance before → after | Keys before → after |
| --- | --- | --- |
| fine | 25 % → 10 % | 0 → 0 |
| rare | 100 % → 30 % | 1 → 0 |
| exquisite | 100 % → 60 % | 1 → 1 |
| legendary | 100 % | 2 → 1 |
| heirloom | 100 % | 3 → 2 |

Evidence: the casual player opened 124 crates on day 1 and banked **29 Charms for 3
sockets** and 23 Keys; by day 7 it was 271 Charms and 223 Keys. A Charm stopped being
an event within the first session, and Keys (which open safes instantly) piled up with
no sink. After: 14 Charms and 7 Keys on day 1, 119 and 70 on day 7, which still fills
Riviera's 3 sockets in the first session. First Charm is unchanged at 14 s because the
FTUE crate at drop 12 forces one (`crateSpawn.ftueScriptedCharm`). The ladder stays
monotonic (a rarer crate is never a worse Charm, Key or income roll; property-tested).
Pacing is unaffected: Charm income only counts slotted Charms, and the sockets fill
either way.

### 2. Riviera made robust to the measured table (`upgrades.ts`, `progression.ts`)

| Lever | Before | After |
| --- | --- | --- |
| `pusherSpeed.effect.perLevel` | 0.04 | 0.06 |
| `coinValue.baseCost` | 50 | 40 |
| Riviera Yacht `bullionThreshold` | 2 600 | 2 800 |
| Salon de Paris `bullionThreshold` | 18 000 | 20 000 |

Evidence: with the shipped model at the physics return (`--return-ratio 0.9`) two targets
missed (5 h 36 min active, day 2.51 casual). A fresh table at 0.9 loses coins on every
drop, so the early game is a race to make the first `pusherSpeed` and `coinValue` levels
pay for themselves. Raising the Riviera threshold alone cannot fix it (the 1.25 model
then drops under 3 h); lowering it alone leaves casual stuck on day 2.50 (sweep:
threshold 1 900 to 2 300 all gave day 2.50 at 0.9). A grid over pusher speed per level
(0.04 / 0.06 / 0.08), coinValue base cost (30 / 40 / 50), coinValue growth (1.12 / 1.14)
and Riviera threshold (2 000 / 2 400 / 2 800, Salon scaled ×7.1) found four
configurations that pass both models; at 200 players the chosen one has the widest
active margin (3 h 07 min and 4 h 24 min against 3 h – 5 h) and keeps the Venue 2 ratio
mid-band (×1.67 and ×1.63). The Salon threshold moves with Riviera's so the ratio stays
put (the earlier 2 800 / 18 000 run gave ×1.45, too close to ×1.4).

`coinValue.effect.perLevel` was the better lever on paper (0.28 passed both models) but
`src/rateEnvelope.test.ts` pins it at 0.2 through the envelope's coinValue scaling; that
file belongs to the config owner, so this pass leaves it alone.

## P-93: offline rate and the 20 starting coins

**Offline rate.** The server settles offline earnings on the **net** active rate: front-edge
winnings minus coins dropped, over the last 30 minutes of play (minimum 10 minutes),
vault payouts excluded (`apps/server/src/routes/offline.ts`). The sim's
`netRatePerSecond` is the same quantity, so the casual numbers above already use it.
02-ECONOMY.md still says "measuredActiveRate" without saying net; see requests below.

**20 starting coins.** They meet "first upgrade within 2 min" **only if the table starts
with a pile on it.** On an empty table (`--empty-table`), all 20 coins go into building a
pile that needs about 145 coins before anything leaves the front edge: the player hits
0 coins with nothing returned, and first upgrade, first album set, both Ascensions and the
season track are never reached (1/7 pacing targets). With the seeded pile the cheapest
line (`pusherSpeed`, 25 coins) is bought at 23 s p90 on the model, 1 min 47 s p90 on the
physics return. No change to `trustFund.startingCoins` is needed; a seeded table is.

## P-14: fusion value

The config is self-consistent with one formula, stated in `src/formulas.ts`:

```
fused value = (sum of the 3 input values) × fusion.bonusMultiplier (1.25)
```

The fused coin's tier (silver for three coppers) is its physical and visual tier; the
ladder face values in `coinTiers` (1, 5, 25, …) are what a coin is worth when it is
**minted** (dropped or spawned), not what a fused coin is worth. So three coppers fuse
into a silver-tier coin worth 3.75, not 5. The only value fusion creates is
`(1.25 − 1) × inputs`, which `sim/properties.test.ts` proves for any tier mix and any
fusion order (drop → fusion chain → front edge conserves value plus exactly that bonus).
02-ECONOMY.md line 27 (`3 × lower tier × 1.25`) is ambiguous between the two readings and
needs the wording above.

The server floors the fused value (`Math.floor(sum × 1.25)`), so a copper fusion credits
3, not 3.75: the bonus is wiped for the commonest fusion and becomes 0.25 coins of
destroyed value per copper triple before multipliers. Reported as a follow-up.

## Property tests (fast-check)

`packages/economy/sim/properties.test.ts`, about 1 s:

- **Coin conservation.** For any seed, return ratio in [0.5, 2], seeded or empty table and
  any mix of play and offline claims, `coins = granted + won + crate income + offline −
  drops − upgrades − forfeited at Ascension`, and coins never go negative. No coin is
  minted while the pile is still building. (Mutation-checked: dropping the upgrade debit
  from the ledger fails it.)
- **Envelope bounds.** For any seed and up to 4 000 ticks, drops per 10 s window and
  front-edge value per 30 s window stay under `rateEnvelopeFor(current table)`; every
  generated envelope row has at least 2× headroom over its sim mean; the committed
  `rate-envelope.json` equals a fresh generation.
- **Fusion.** Fused value minus inputs is exactly `(bonus − 1) × inputs` for any tier mix
  and multiplier; any drop → fusion chain → front-edge sequence conserves value plus the
  bonuses.
- **Odds.** Any table that sums to `ODDS_SCALE` shows odds-sheet rows that sum to 100 %;
  every percent label reads back as exactly the weight the server rolls; every shipped
  table sums to 100 % and every Charm chance is on the odds scale; the crate reward
  ladder is monotonic.
